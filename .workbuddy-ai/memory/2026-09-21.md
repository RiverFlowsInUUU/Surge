### Surge DNS 泄露的「三条出口」模型（本项目的核心抽象，可复用）

| 出口 | 触发 | 必然性 | 收口 |
|:--|:--|:--|:--|
| ① 引导解析 | `encrypted-dns-server`/`dns-server` 写主机名 | 冷启动必然 | 端点写 IP 字面量；`dns-server` 禁 `system` |
| ② 旁路设备 | HomePod/AppleTV 等直发明文 `:53` | 设备在线必然 | `hijack-dns` |
| ③ 规则触发 | IP 类规则不带 `no-resolve` | 每个新域名 | 全带 `no-resolve` |

### 本项目最硬的两条纪律（已固化成测试）

1. **`no-resolve` 与「域名体量足够的国内直连集」必须成对交付。**
   给 IP 规则补 `no-resolve` 会**同时**关掉「解析后判 IP 归属」这条直连路径 ——
   只交一半，国内域名整片落 `FINAL → Proxy`。判据是**数域名条目**，不是看规则集名字
   （反例：`ChinaMax.list` 12472 条里只有 64 条是域名）。
2. **`pre-matching` 的策略必须是字面量 REJECT 族**，不能是策略组 ——
   组在运行时可能解析成 `DIRECT`，Surge 会**直接拒绝加载整份配置**。

### 上传 GitHub 空仓库的坑（重要，可复用）

- 对**空仓库**调 `POST /git/blobs` 返回 **`409 Git Repository is empty`**（不是 404）。
- 解法：先用 Contents API `PUT` 写一个占位文件「点燃」仓库，之后才能走
  blobs → tree → commit → ref 一次推整棵树。
- 「点燃」之后分支已存在 → `POST /git/refs` 会 **422 Reference already exists**，
  要改用 `PATCH /git/refs/heads/<branch>` + `force: true` 强推。
- token scope 只有 `public_repo` ⇒ 能建 **public** 仓库、不能建 private。
- 验证线上真实状态用 `GET /git/trees/main?recursive=1`，不要信本地。

#### Surge 与 egern 的三处本质差异（**查官方文档得来，不是猜的**）

1. **`flatten` → `include-other-group`**。官方定义：`include-other-group="group1,group2"`
   **"includes the resolved member policies from other policy groups"** —— 语义与 egern 的 flatten 一致，
   且可递归、可与 `policy-regex-filter` 组合。比机械地硬列组名干净。
2. ⚠️⚠️ **Smart 策略组不可以用其他组作子策略**（官方原文），也不可当 `url-test`/`load-balance` 的子策略。
   ⇒ **老板原计划的「把地区组当 smart 组的子节点」在 smart 上不合法**。
   最终：**app 组（ChatGPT/Claude/AI/Final）用 `select`**（可列组名，合法）；
   **`Proxy`/`Smart`/地区组/`MAX` 用 `smart` + `include-other-group`**（本来就是选节点的，不需要嵌套组名）。
   已事先向老板说明这个偏差，他接受了。
3. ⚠️ **`policy-regex-filter` 对显式列出的成员不生效** —— 官方：只作用于
   `policy-path` / `include-all-proxies` / `include-other-group`。老板是在 `[Proxy]` 里手写节点的，
   所以地区组**必须加 `include-all-proxies=true`**，否则手写节点根本进不了地区组。

其他沿用：`external` → `policy-path` + `update-interval=86400` + `hidden=true`（`hidden` 只是藏菜单，**仍可被 `include-other-group` 引用**）。
空策略组 Surge 允许存在、不会拒绝加载，但指向空组的规则会失效。

### 顺带查出的第二个真窟窿：Apple

`SYSTEM` 内置集合只覆盖激活 / 推送 / 配对核心主机。
`courier.push.apple.com` / `developer.apple.com` / `gateway.icloud.com`
当时**落到兜底 `Final → Proxy`**。egern 用的是 `Apple_All_No_Resolve.list → DIRECT`。

⚠️ **必须用 `No_Resolve` 版**（egern v7 的核心改动）：`Apple_All.list` 里有 13 条
`IP-CIDR` 没带 `no-resolve`，而这条规则排在 IP 类规则**之前**、策略又是 `DIRECT`
⇒ 每个未命中的域名经过这里都会被**强制解析一次**。那次解析走本地 DNS = 泄露本身。
症状：dnsleaktest 里「判定显示 default→Final→Proxy，但 upstream 显示 bootstrap」。

两条配置都改了。审计器新增 `APPLE_PROBES`（6 个）判据。
`audit_ruleset_content.py` 输出确认：`Apple_All_No_Resolve.list 域名 1567 / IP 13`，
13 条 IP **全部带 no-resolve**（0 high）。

> 注意：Apple 流量走代理**不报错**，只变慢 + 推送偶发延迟 ——
> 属于用户不会主动报障、但体验确实变差的一类，**只能靠审计钉住**。

### 修法（egern 语义 → Surge 写法）

| egern | Surge |
|:--|:--|
| `policies: [Proxy]` + `flatten: true` | `select, Proxy, <7 个地区组…>` |
| `Microsoft` / `WeChat` 直连优先 | `select, DIRECT, Proxy, <地区组…>` |
| `Google` 首项是 `Gemini` 组 | `select, Gemini, Proxy, <地区组…>` |

**`WeChat` 单列一组的意义不是"能切换"，是"接住它"** ——
把它从 `Final` 兜底里摘出来，避免微信走代理绕远 + 触发风控。
