# 分流版：按应用 + 按地区选路

> 本文是 `profiles/routing_v3.conf` 的设计说明。
> 只看「怎么用」的话，README 的[两份配置](../README.md#-两全其美皆合心意)就够了；本文讲的是**为什么长这样**。

---

## 1 · 它和 `lazy.conf` 是什么关系

两份配置**不是版本关系**，是**分工关系**。选一份用，不要叠加。

| | `lazy.conf` | `routing_v3.conf` |
|:--|:------------|:---------------|
| 定位 | 懒人版 | 分流版 |
| 策略组 | 3 个 | 26 个 |
| 规则 | 11 条 | 24 条 |
| 出口粒度 | `Proxy` / `AI` / `AD` | 按**应用**分（ChatGPT / Google / GitHub …），组内再按**地区**分 |
| 适用 | 只想通、不想调 | 想让 ChatGPT 走美国、Claude 走台湾、微信直连 |

**共同点（刻意保证，由测试逐字断言）**：

- `[General]` 的 16 个 DNS 相关键**逐字相同** —— 防泄露结构不因分流粒度而变；
- 同样带广告白名单 + `pre-matching` 拦截；
- 规则顺序遵守同一条铁律（白名单 → 拦截 → 域名类直连 → IP 类 → 兜底）。

> 📌 「lazy 与 routing 的 DNS 段必须逐字相同」由
> `skill/tests/architecture.sh` 的 ②-b 段断言。
> 想只改一份的 DNS 段？测试会拦下来。

## 2 · 移植自 Egern v3，但有三处必然的差异

分流结构整体借鉴 [Egern](https://github.com/RiverFlowsInUUU/Egern) 的 `v2.5`。
**规则集可以直接复用**——Egern 用的那批 ruleset 本身就是 Surge 格式的，Surge 完全支持。

但有三处字段在 Surge 里**没有对应物**，必须改写。这三处不是"风格差异"，是硬约束。

### 2.1 `flatten` —— Surge 没有，但有个更准确的对应物

Egern 的 `flatten: true` 作用是把「Proxy」这个**组名**在求值时替换成组内**全部具体节点**，
好让 `smart` 能逐个节点测速。

Surge 的等价物是 **`include-other-group="X"`**。官方原文：

> `include-other-group="group1,group2"` includes the **resolved member policies** from
> other policy groups.
>
> — [Policy Including · manual.nssurge.com](https://manual.nssurge.com/policy-groups/policy-including.html)

「resolved member policies」= 已经解析出来的成员，与 `flatten` 语义一致（可递归、可配正则）。

```ini
# ✅ 正确：smart 拿到的是具体节点，能逐个测速
Proxy = smart, include-other-group="Airport"

# ❌ 错误：smart 的成员是「Airport」这一个组名单位，测不到组内节点
Proxy = smart, Airport
```

### 2.2 ⚠️ Smart 组**不能**拿组名当子策略

这是本次移植**最重要的一条限制**，官方明文写着：

> Smart 策略组**不可以使用其他组作为子策略**，也不可以用作 `url-test`/`load-balance` 组的子策略。
> 但是可以使用 `include-other-group` 参数从其他组复制子策略。
>
> — [Smart 智能策略组 · Surge Knowledge Base](https://kb.nssurge.com/surge-knowledge-base/zh/guidelines/smart-group)

所以「把地区组当子节点塞进各 app 组」这个做法，只在 `select` 组上成立 —— 而本配置**刻意不用它**。

> ⚠️ **留痕：这里曾经写错过。**
> 早期版本把应用组写成 `select, Proxy, Hong Kong, USA, …`（把地区组名一个个列成成员），
> 理由写成"这样面板上能点进地区再选"。
> **这是自创写法，与 Egern 不符** —— Egern 的应用组 `policies` 里**只有 `[Proxy]` 一项**
> （外加 `flatten: true`），从来没有地区列表。
> 它当时能过全部测试（成员可解析、规则可解析），因为"能解析"与"语义对"是两件事。
> 现在已改成与 Egern 逐字对齐的 `include-other-group="Proxy"`。

**Egern 的 `flatten: true` 到底做什么**：

```yaml
- fallback:
    name: ChatGPT
    policies:
    - Proxy          # ← 只有这一项
    flatten: true    # ← 把「Proxy」这个**组名**展开成它内部的**全部具体节点**
```

即：`flatten` 是"把组名替换成组内全部节点"，让 `fallback` / `smart` 能做**节点级**的顺序尝试。
**Surge 没有 `flatten`**，对应物就是 `include-other-group="X"` —— 官方原文：

> includes the **resolved member policies** from other policy groups

语义一致（复制已解析出的成员），可递归、可配正则。

本配置因此按**用途**分两种写法 —— 这不是随意的风格差异：

| 用途 | 写法 | 为什么 |
|:-----|:-----|:-------|
| 需要 smart **自动选优** | `smart` + `include-other-group` | 只有拿到具体节点，smart 才能逐个测速 |
| 需要**复制 Proxy 全部节点、且面板可手动接管** | `select` + `include-other-group="Proxy"` | **与 Egern 逐字对齐** |

```ini
# ① Smart / 7 个地区组 / MAX —— 用 include-other-group 拿具体节点
Smart       = smart, include-other-group="Airport"
Hong Kong   = smart, include-all-proxies=true, include-other-group="Airport", policy-regex-filter=(?i)🇭🇰|香港|…
MAX         = smart, include-all-proxies=true, include-other-group="Airport", policy-regex-filter=(?<![\d.])0\.\d*[1-9]

# ② 应用组 —— 复制 Proxy 已解析的成员（= Egern 的 policies:[Proxy] + flatten）
ChatGPT     = select, include-other-group="Proxy"
Claude      = select, Taiwan, include-other-group="Proxy"   # Egern 的 Claude 首项是 Taiwan
```

> 📌 **一个必须说清的差异**：Egern 的应用组用的是 `fallback` / `smart`（**自动**故障转移），
> Surge 的 `select` 是**纯手动**类型。
> ⇒ 本配置的应用组 = 「默认走 Proxy 的全部节点 + 面板上可手动改」，**没有自动故障转移**。
> 想要自动选优，把某个组换成 `smart, include-other-group="Proxy"` 即可
> （代价：面板上不能再手动挑节点）。
> 这是**能力差异**，不是配置疏漏 —— 已写明，不假装两边等价。
>
> 📌 需要手动指定地区时，在**面板上**把该应用组切到 `Taiwan` 等地区组即可 ——
> 比把地区组列进成员更干净：成员表保持与 Egern 一致，手动干预走面板。

### 2.3 `select` 组引用另一个组的两种写法

Surge 的 `select` 组允许成员是**另一个组名**，也允许 `include-other-group` 把对方**已解析的成员**复制进来。两者不等价：

| 写法 | 面板表现 | 求值结果 |
|:-----|:---------|:---------|
| `select, Proxy` | 面板上多出一个「Proxy」条目，可点进去 | 指向 Proxy 组（**动态**，Proxy 改了它跟着改） |
| `select, include-other-group="Proxy"` | 面板上平铺出 Proxy 的**全部具体成员** | 复制 Proxy 当前解析出的成员（**求值期快照**，可递归展开） |

Egern 的 `policies: [Proxy] + flatten: true` 对应**后者**，本配置即采后者。

### 2.4 `external` —— 用 `policy-path` 替代

Egern 的 `external: Airport-A` 是订阅槽位。Surge 没有这个字段，官方等价写法是 **`policy-path`**：

```ini
Airport = select, policy-path=https://<你的订阅>, update-interval=86400, hidden=true
```

- `update-interval` 单位是秒，**默认 86400**。显式写出来是为了让"规则集/订阅会按天刷新"这件事在文件里可见。
- `hidden=true` 只是不在菜单里显示，**不影响它被 `include-other-group` 引用**。

## 3 · 分组层次

```
① 总入口
Proxy                     select  ← 总出口；首项是 MAX（低倍率池），与 Egern 一致
                                └─ 成员 = MAX, Smart, 7 个地区组（都是组名）
Smart                     smart   ← 全节点池（不含 MAX 与地区组）
                                └─ include-other-group="Airport"

② 应用组（全部 select + include-other-group="Proxy"）
ChatGPT / Gemini / AI /
Spotify / YouTubeMusic / YouTube /
GitHub / Telegram / Twitter
                                ← Egern 的 policies:[Proxy] + flatten:true 的对应物
Claude                    select  ← 首项 Taiwan（与 Egern 一致）
Google                    select  ← 首项 Gemini（与 Egern 一致）
Microsoft                 select  ← 首项 DIRECT（与 Egern 一致）

③ 订阅槽位 + 开关
Airport                   select  ← 订阅入口（hidden，不被规则直接引用）
                                └─ policy-path=<订阅 URL>
WeChat                    select  ← 首项 DIRECT；把微信从兜底里摘出来（**功能上属应用组**，见下方 📌）
AD                        select  ← 独立手动开关（REJECT / DIRECT）

④ 地区组 + 精选
Hong Kong / USA / Japan / Taiwan /
Singapore / Korea / Other Regions /
MAX                       smart   ← 地区筛选（filter 正则 / 负向断言）
├─ include-all-proxies=true     ← 让 [Proxy] 里的本机节点也参与筛选
└─ include-other-group=Airport  ← 让订阅节点参与筛选

⑤ 兜底
Final                     select  ← 兜底
```

> ⚠️ **段内顺序与 Egern v3 逐位对齐**，由 `skill/tests/architecture.sh` 的 ④ 断言守着。
> 排布原则是「**先写引用别人的，后写被引用的**」—— 读配置时先看到"谁在用"，再看"节点从哪来"。
> 注意这会产生**前向引用**（`Proxy` 引用它后面才定义的地区组）。
> Surge **允许**前向引用 —— 官方文档的 `include-other-group="A,B"` 示例本身就是前向引用。

> 📌 **`③` 是按「位置」切的分节，不是功能归类** —— 别被编号误导：
> `WeChat` 出现在 `③` 里，只因为 Egern v3 就把它排在「订阅槽位」与 `AD` 之间
> （`architecture.sh` ④ 断言守着这个顺序），**不代表它是个开关**。
> 判据是**有没有被规则引用**：
>
> | 组 | 被规则引用？ | 定性 |
> |:---|:-------------|:-----|
> | `WeChat` | ✅ `RULE-SET,…,WeChat.list,WeChat` | **应用组**（首项 `DIRECT`，把微信从兜底摘出来） |
> | `AD` | ❌ 刻意设计成不被引用（[`DetailsReadme` §13.3](../DetailsReadme/DetailsReadme.md)） | 本仓**唯一**的「开关」 |
>
> 所以应用组是 **13 个**（不是 12）：`②` 里那 12 个 + `WeChat`。
> 应用规则 **14 条**（`Anthropic.list` 与 `Claude.list` 同指 `Claude` 组）。

**应用组的首项 = 默认取向**，逐组对齐 Egern v3：

| 应用组 | 首项（默认） | 依据 |
|:-------|:------------|:-----|
| `ChatGPT` / `Gemini` / `AI` | `Proxy` | Egern 的 `policies: [Proxy], flatten: true` |
| `Claude` | `Taiwan` | Egern 里 Claude 首选台湾组 |
| `Google` | `Gemini` | Egern 的 `Google` 组 `policies: [Gemini, Proxy]` |
| `Spotify` / `YouTubeMusic` / `YouTube` | `Proxy` | 同 ChatGPT |
| `Telegram` / `Twitter` | `Proxy` | 同 ChatGPT |
| `GitHub` | `Proxy` | 同 ChatGPT |
| `Microsoft` | `DIRECT` | Egern 的 `Microsoft` 是 `DIRECT` 优先 |
| `WeChat` | `DIRECT` | Egern 的 `WeChat` 是 `DIRECT` |

> 📌 **为什么 `WeChat` 也要单列一个组**（看起来是"直连，用不着分组"）：
> 它的作用是**把微信从兜底里摘出来**。没有这一组时，微信域名会落到 `Final → Proxy`，
> 走代理不仅绕远，还可能触发风控。分组的意义不是"能切换"，而是"接住它"。

### 为什么地区组要同时写 `include-all-proxies` 和 `include-other-group`

因为 `policy-regex-filter` 对**显式列出的成员无效**。官方原文：

> It applies to members from `policy-path`, `include-all-proxies`, and `include-other-group`,
> but **not to explicitly listed members**.
>
> — [Policy Including](https://manual.nssurge.com/policy-groups/policy-including.html)

⇒ 你手写在 `[Proxy]` 里的节点，只有通过 `include-all-proxies=true` 才会被正则筛到。
少了它，地区组永远只能筛订阅里的节点。

## 4 · 地区名怎么筛（正则）

每个地区组用一条 `policy-regex-filter` 匹配节点名。**节点名里要有地区关键词**，筛选才生效。

`routing_v3.conf` 的占位节点名刻意做成 `Node-HK-01` / `Node-US-01` 这种形态，
就是为了让你一导入就能看到地区组筛到了东西。

### 关键词不匹配怎么办

如果你的节点名里没有地区关键词（比如机场给的是 `Node-1` / `Line-A`），
把 filter 换成**你认得的写法**即可。两种常见情形：

| 你的节点名长这样 | filter 怎么写 |
|:-----------------|:--------------|
| `HK-01` / `hk01` / `HongKong-1` | `(?i)^HK` 或 `(?i)hongkong` |
| `🇭🇰 香港 01`（带 emoji + 中文） | 默认的那条就够用 |
| `p01-hk` / `s02-us`（地区在尾部） | `(?i)hk` / `(?i)us` |

> ⚠️ **别写得太宽**。`(?i)us` 会同时命中 `Russia` / `Belarus` / `AUStralia`；
> `(?i)hk` 相对安全，`(?i)j p`（中间有空格）会失效。
> 保守做法是用 `\b` 锁词边界：`(?i)\bhk\b`。

### ⚠️ `Other Regions` 是最大的一处维护负担

它的 filter 是**负向断言**，把另外 6 个地区组的关键词**逐字抄了一遍**：

```ini
Other Regions = smart, …, policy-regex-filter=(?xi)^(?!.*(?:🇭🇰|香港|…|群组)).+$
```

这是有意为之（负向断言要求"排除以上全部"），但代价是：
**任何地区组新增/修改关键词，都必须同步改 `Other Regions`。**

漏改的后果不报错、面板上也看不出：含该关键词的节点会**同时**出现在它自己的地区组和
`Other Regions` 里，两个组的内容不再互斥。

> ✅ **自动校验**：
> ```bash
> python skill/scripts/audit_region_filters.py profiles/routing_v3.conf
> ```
> 它会把 6 个地区组的关键词集合与负向断言逐个比对，报出缺失项。
> 这个脚本的判别力由回归测试的 `fixtures/bad_region_filter.conf` 守着
> （那份 fixture 刻意少同步一个关键词，期望被报出）。
>
> ⚠️ 这份拷贝**在配置层面消灭不掉** —— Surge 的 filter 不支持引用变量，正则是字面量。
> 只能靠脚本守。

## 5 · 规则顺序

24 条，比 lazy 多 13 条 —— 应用分流从 1 条（`AI.list`）拆成 **14 条**（13 个目标组：`Anthropic.list` 与 `Claude.list` 指向同一个 `Claude` 组）；此外**内网段提前到应用之前**、`WeChat` 后移到 `Apple` 之后，与 Egern v3 的顺序逐位对齐。

| # | 分类 | 规则 | 去向 |
|:-:|:-----|:-----|:----:|
| ①②③ | 🛡️🚫 白名单 / 广告拦截 ×2 | `surge-white-guard.list` / `surge-ads.list` / `AWAvenue-Ads-Rule` `pre-matching` | 直连 / 拒绝 |
| ④⑤ | 🏠 内网 | `LAN` / `private.txt` | 直连 |
| ⑥ | 💬 ChatGPT | `OpenAI.list` | `ChatGPT` |
| ⑦ | ✨ Gemini | `Gemini.list` | `Gemini` |
| ⑧⑨ | 🎭 Claude | `Anthropic.list` + `Claude.list` | `Claude` |
| ⑩ | 🤖 其余 AI | `AI.list` | `AI` |
| ⑪ | 🎵 Spotify | `Spotify.list` | `Spotify` |
| ⑫ | 🎶 YouTube Music | `YouTubeMusic.list` | `YouTubeMusic` |
| ⑬ | ▶️ YouTube | `YouTube.list` | `YouTube` |
| ⑭ | 🐙 GitHub | `GitHub.list` | `GitHub` |
| ⑮ | 🔎 Google | `Google.list` | `Google` |
| ⑯ | 🪟 Microsoft | `Microsoft.list` | `Microsoft` |
| ⑰ | ✈️ Telegram | `Telegram.list` | `Telegram` |
| ⑱ | 🐦 Twitter / X | `Twitter.list` | `Twitter` |
| ⑲⑳ | 🍎 Apple 服务 | `SYSTEM` + `Apple_All_No_Resolve.list` | 直连 |
| ㉑ | 💚 WeChat | `WeChat.list` | `WeChat` |
| ㉒ | 🇨🇳 国内直连 | `direct.txt`（11 万条域名） | 直连 |
| ㉓ | 🌏 GeoIP CN | 中国 IP | 直连 |
| ㉔ | 🌐 兜底 | `Final` | `Proxy` |

> 📌 与 `lazy.conf` 的两处规则差异：本版**没有**游戏机主机名三条
> （`nintendo.net` / `playstation.net` / `xboxlive.com` → `Proxy`）—— 已按 Egern v3 对齐删除；
> `always-real-ip` 仍保留，这些主机名照旧拿到真实 IP，去向改为 `FINAL → Final`。

**两条顺序铁律**：

1. **⑥–⑩ 必须排在 ㉒ 之前** —— 否则「域名恰好被国内清单收录的 AI 服务」会被直连接走。
2. **⑪–㉑ 也必须排在 ㉒ 之前**，其中 **`GitHub.list`（⑭）最敏感**：`github.com`
   同时被 `direct.txt` 收录，排到后面就接不到它，"GitHub 走代理"直接失效。

都是「越具体的越靠前」这条铁律的直接应用。

### 兜底为什么不直接写 `Proxy`

`FINAL,Final,dns-failed` 里 `Final` 是一个 `select` 组（首项是 `Proxy`）。
多挂一层组是为了让你**在面板上还能改兜底去向**，代价是零。

## 6 · 内地直连：与 `lazy.conf` 完全一致

Egern v3 用 `GEOIP, CN, DIRECT, no_resolve` 一条兜住国内，
本配置**没有照搬**，而是沿用 `lazy.conf` 的两条：

```ini
RULE-SET,…/direct.txt,DIRECT,no-resolve   # 11 万条纯域名，主承重墙
GEOIP,CN,DIRECT,no-resolve                # 已是 IP 的连接
```

**为什么**：`GEOIP,CN,no-resolve` 不匹配域名（`no-resolve` 的语义就是"只用已解析的 IP"），
所以国内**域名**必须由一份域名条目足够的清单承接。

| | Egern v3 | 本配置 |
|:--|:-----------|:-------|
| 国内域名 | `direct.txt`（同款） | `direct.txt` |
| `.cn` 兜底 | 额外一条 `domain_suffix: cn` | 不需要（`direct.txt` 已含 `.cn`） |
| IP 兜底 | `GEOIP, CN` | 同款 |

Egern 那条 `domain_suffix: cn` 在这里是冗余的 —— 它存在的理由是「不依赖规则集是否加载成功」，
而本配置与 `lazy.conf` 共用同一套清单，一致性由测试保证。

|:-----|:------|:-----|
| `audit_region_filters.py` | 7 个地区组的关键词是否同步、是否互斥、类型是否 smart | 9 通过 / 0 失败 |
| `audit_routing_coverage.py` | 拿真实域名走一遍：8 个境外探针必须落进**各自的专属组**（`chat.openai.com`→`ChatGPT`、`github.com`→`GitHub`…），另有 6 个 Apple 探针必须直连 | 39 通过 / 0 失败 |

> 📌 覆盖审计对分流版用的是**另一套期望表**（精确到应用组名）。
> 判据是"文件里实际定义了哪些组"，不是文件名 —— 所以把分流版改名也不会让期望失配。
> ⚠️ 期望值刻意精确到组名，**不是**放宽成"只要不是 DIRECT 就行"：
> 后者会让「整片走兜底」的坏配置假通过。
>
> 📌 **这张表曾经暴露过本次的漏项**：补组之前，有 6 个探针的期望值就是 `FINAL` ——
> 那正是在记录「Spotify / Google / YouTube / Telegram / Twitter / GitHub 全都没接住」这个事实。
> 补完组后期望值同步收紧到专属组名，将来谁把组删了都会立刻报警。

## 8 · 已知边界

| 项 | 说明 |
|:---|:-----|
| 🕳️ 空地区组 | 节点名不含该地区关键词时，该组为空。Surge **不会**因此拒绝加载，但指向它的规则会断流。导入后到面板上确认哪几个组是空的 |
| 🔁 `Other Regions` 关键词双份 | 上面 §4 已述，靠脚本守 |
| 🆔 `MAX` **放进** `Proxy` 首项 | 与 Egern v3 完全一致（Egern 的 `Proxy.policies[0]` 就是 `MAX`）。代价要说清：**默认出口会优先落在低倍率节点上**，更省钱但可能更慢。不想这样就把 `MAX` 从首项挪到末尾或删掉 |
| 🚫 `https` 节点不支持 UDP | 本配置里 `Node-Relay-*` 是 `https` 类型，落到它们上的 UDP 会被拒绝。这也是它们只放在 `Claude` 组、不做默认出口的原因 |
| 🍎 `Apple` 没有独立策略组 | 与 Egern 一致：Apple 走的是 `Apple_All_No_Resolve.list → DIRECT`，**不需要组**（没有"给 Apple 挑地区"这个需求）。如果你的场景需要，照 §2.2 复制一个 `select` 组即可 |
| 🛬 `Airport-A` / `Airport-B` 合并为一组 | Egern v3 留了两个订阅槽位，本配置合并为单个 `Airport`。要双槽位就再复制一个 `select` 组，改掉 `policy-path`，并把组名加进 `Proxy` / `Smart` / 地区组的 `include-other-group` 列表 |

> 📌 **曾经的做法（留痕）**：本版最初只做了 3 个应用组（`ChatGPT` / `Claude` / `AI`），
> 没有 `Gemini` / `Spotify` / `YouTube` / `GitHub` / `Google` / `Microsoft` /
> `Telegram` / `Twitter` / `WeChat` 这 9 组。
> 结果是这些应用的流量**全部落到兜底 `Final → Proxy`** ——
> 「能通」但「按应用分流」这个卖点是空的，而且和 Egern v3 的取向不一致
> （Egern 里 `Microsoft` / `WeChat` 明确直连）。
> 漏项的发现方式值得记一笔：`audit_routing_coverage.py` 里那些**期望值是 `FINAL`** 的探针
> 就是证据 —— 审计器一直在如实记录"这个域名没人接住"，只是当时把它当成了预期行为。

> 📌 **曾经的做法（留痕）：`MAX` 曾经**不**在 `Proxy` 首项，应用组曾经列地区组。**
> 两处都是**自创写法**，与 Egern 不符，现已全部回退到与 Egern 逐字对齐：
>
> | 项 | 曾经这样做 | 为什么错 | 现在 |
> |:---|:-----------|:---------|:-----|
> | `MAX` 位置 | `Proxy = select, Smart, …, MAX`（`MAX` 排后面） | Egern 的 `Proxy.policies[0]` 是 `MAX`；"默认出口是否走高倍率该由用户决定"是我自己加的理由，Egern 没有 | `Proxy = select, MAX, Smart, …` |
> | 应用组成员 | `select, Proxy, Hong Kong, USA, …`（列地区组） | Egern 的应用组 `policies` 只有 `[Proxy]`；"列地区组好在面板点进地区"是我读错 `flatten` 后自创的 | `select, include-other-group="Proxy"` |
> | 段内顺序 | 总入口 → 地区组 → 应用组 → 兜底 | 没有对齐 Egern 的「引用在前、被引用在后」 | ① 总入口 → ② 应用组 → ③ 订阅槽位 → ④ 地区组 → ⑤ 兜底 |
>
> ⚠️ 这三处**当时全部通过了测试** —— 成员能解析、规则能解析、地区正则互斥。
> 这说明"能过审"不等于"语义对"。真正的对账方式是把**参照物的成员表**逐项拉出来比，
> 而不是只比组名集合。现在 `skill/tests/architecture.sh` 的 ④ 已把顺序钉死。
