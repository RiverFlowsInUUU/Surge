# 06 · 实测数据与版本谱系

> 本篇记录**改配置之前先量一遍**得到的数字。
>
> 为什么要有这篇：DNS 泄露方案有太多"看起来对"的写法，光靠读配置读不出谁快谁省电。
> 这些数字决定了模板里几处看起来"多此一举"的取舍 —— 比如 `proxy-test-url` 为什么
> 不用 `gstatic.com`、`pre-matching` 为什么值得单开一条规则。

---

## 1 · 泄露面的量化

同一台设备、同一次冷启动，只改一处配置，看明文 `UDP:53` 的出现次数。

| 配置状态 | 明文 :53 次数 | 说明 |
|:---------|:-------------:|:-----|
| 裸连（无 Surge） | 全程 | 基线，不作对数 |
| Surge 默认 DNS | 数十次 | 系统 DNS 查询 + 旁路设备 |
| 仅加 `encrypted-dns-server` | ~ 12 次 | 端点主机名的**引导解析**仍然明文 |
| 再加 `hijack-dns` | ~ 3 次 | 旁路设备收口，剩引导与规则触发 |
| 再加 IP 规则 `no-resolve` | **0** | 三处收口完成 |

> ⚠️ 这些是单机单次抓包的读数，**只用于判断"有没有收口"，不要当成绝对值**。
> 不同系统版本、不同路由器环境差异很大。要复现请自己抓一遍。

关键在于**逐项下降的拐点**：加了 `no-resolve` 之后从 3 掉到 0，说明规则触发的解析
才是最后那一条通路，也说明前两步单独做都不够。

## 2 · `pre-matching` 的收益

`pre-matching` 让 REJECT 在 **DNS 查询 / TCP SYN 阶段**就生效，不建连、不解析。
拿广告拦截那 3891 条规则集量：

| 指标 | 不开 `pre-matching` | 开 `pre-matching` |
|:-----|:-------------------:|:-----------------:|
| 命中域的 DNS 查询 | 走完解析再拒 | 查询即拒 |
| 每条命中的建连次数 | 1（TCP 握手） | **0** |
| 批量规整广告页面的完成时间 | 基线 | 明显更短 |

这是**全模板最大的一笔电池优化**，原因是它省掉的不只是带宽，还有"解析 → 建连 →
等首字节 → 丢弃"这一整串唤醒。移动端省电的关键从来不是省流量，是少唤醒。

### 2.1 但 `pre-matching` 有个硬约束

`pre-matching` 的规则，**策略必须是字面量 `REJECT` 家族**，不能是策略组。

原因：预匹配发生在**还来不及决定出口**的阶段。策略组的结果依赖运行时评分
（`smart` 会按首字节延迟选节点），而这一步在预匹配阶段还没发生。更糟的是，
若把组名写进 `pre-matching`，而该组在运行时可能解析成 `DIRECT`，Surge
**会直接拒绝加载整份配置**。

⇒ 所以本模板的广告拦截写的是字面量 `REJECT`，而旁边那个 `AD = select, REJECT, DIRECT`
组**不由任何规则引用**，只给你在面板上手动切。这两者看起来重复，实际是两件事。

## 3 · `smart` 组评分的三个维度

`smart` 不是"取最低延迟"，它按三个信号打分：

| 维度 | 权重体现 | 为什么算它 |
|:-----|:---------|:-----------|
| 真实连接首字节延迟 | 主项 | 比 ping 更贴近实际体验 |
| TCP 重传率 | 每 1% 约折算 50 ms | 丢包比延迟更致命，按时延折算才能进同一套评分 |
| UDP 响应延迟 | 单列 | `https` 类型**不支持 UDP 中继**，UDP 表现必须单独看 |

重测间隔 5 分钟，并**按站点记住最优策略** —— 所以你会看到 `smart` 对
「同一个节点，访问 A 站快、访问 B 站慢」这种情况有自适应能力。

> 📌 由此得出一个模板里的硬规则：**`https` 类型的节点不要放进承担 UDP 的组**。
> 本模板把 `Node-C` / `Node-D`（都是 `https`）放进 `AI` 组，因为 AI 流量的
> 主要诉求是稳定长连接与不被降级，不靠 UDP。反过来，需要 UDP 中继的场景
> （游戏、部分 QUIC 应用）要走 `hysteria2` 的节点。

## 4 · 代理测试端点的选择

这是本模板相对原始懒人配置**唯一一处实质改动**，值得单独说明。

| 端点 | 域名性质 | 每次测速时的解析 | 结论 |
|:-----|:---------|:-----------------|:-----|
| `http://www.gstatic.com/generate_204` | 境外 | 一个**境外域名**，且不在任何分流里 → 走代理解析 | ❌ |
| `http://connect.rom.miui.com/generate_204` | 境内 | 被 `direct.txt` 接住 → 直连解析 | ✅ |

`proxy-test-url` 不是一次性动作 —— 它**每 5 分钟被每个组各跑一遍**（`smart` 的重测）。
用境外端点意味着：一个持久的、周期性的、必然发生的**境外域名解析面**。

换成境内外端点后：
- 解析被 `direct.txt` 接住，走直连，不进代理链；
- 国内 204 端点的 RTT **方差小**，测出来的分数更能反映节点本身而不是链路抖动。

⚠️ 注意区分：`proxy-test-url` 决定**测速用什么**，`proxy-test-udp` 决定**UDP 测速用什么**。
后者本模板用的是 `apple.com@1.1.1.1`，它走的是 UDP 探测，不产生域名解析面
（`1.1.1.1` 是字面量）。

## 5 · 版本谱系

两个版本**共享同一份 DNS 段**，差异只在分流。这是刻意的 —— 防泄露是目标，
分流是姿态，把两件事绑在一起会让"我只想要防泄露"的人被迫接受一套分流哲学。

| | `v1` | `v0` |
|:--|:-----|:-----|
| 策略组 | `Proxy` / `AI` / `AD` | `Proxy` / `Final` |
| `Proxy` 组类型 | `smart` | `select` |
| `[Rule]` 条数 | 12 | 7 |
| AI 分流 | ✅ `AI.list` → `AI` 组 | ❌ 合流进 `Proxy` |
| 白名单守卫 | ✅ 43 条 | ❌ 移除 |
| 广告拦截 | ✅ `pre-matching` | ✅ `pre-matching`（保留） |
| 游戏主机 real-ip 规则 | ✅ 3 条 | ❌ 移除 |
| `[URL Rewrite]` | ✅ | ❌ 移除 |
| **DNS 段** | **逐字相同** | **逐字相同** |

### 5.1 为什么不把 `v0` 做成"更少规则的 `v1`"

如果 `v0` 只是 `v1` 的精简版，那它必然会随着 `v1` 演进被落下。
本模板的做法是：**把"不许分裂"的东西写成回归测试**。
`skill/tests/architecture.sh` 会逐字节比对两个版本的 DNS 段 16 个键 —— 一旦有人
只改了 `v1` 的 DNS 段，测试立刻红。

这也是 Egern 项目留下的教训：**同一件事写在两个地方，早晚会只改一处。**

### 5.2 `v0` 移除白名单守卫的代价，必须写在文件里

`v0` 末尾有一段显式注释列出三点代价。写成注释而不是只写进文档，是因为
**改动发生的地方和代价提示应该在同一个文件里** —— 否则改的人不会去看 `docs/`。

## 6 · 数据是怎么来的 / 怎么复现

本仓库**刻意不挂 CI / 任何自动化**（理由见 [`skill/README.md`](../skill/README.md)），
所有数字都是本地跑出来的：

```bash
# 结构审计（不联网）
python skill/scripts/check_surge_dns.py profiles/v1.conf

# 规则集内容审计（需要联网，拉一遍所有 RULE-SET）
python skill/scripts/audit_ruleset_content.py profiles/v1.conf

# 分流覆盖（需要联网，拿域名走一遍规则）
python skill/scripts/audit_routing_coverage.py profiles/v1.conf

# 全部一起
bash skill/tests/run.sh
```

当前读数见 [`08-审计读数`](08-审计读数.md)。

> ⚠️ 抓包类数字（§1）**没有脚本**，必须人工用 Charles / Stream / Wireshark 之类抓。
> 审计脚本只覆盖**静态可判定**的部分 —— 这是刻意的边界，不是遗漏。
